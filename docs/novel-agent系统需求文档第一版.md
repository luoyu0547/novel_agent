# novel-agent系统需求文档第一版

可以先把这个系统理解成：**不是“自动写完整本小说”，而是“像 Cursor 辅助代码一样，辅助作者长期管理、规划、续写、检查长篇小说”**。

## 一、核心需求拆解

### 1. 长期记忆能力

目标不是简单保存聊天记录，而是让系统能知道：

| 记忆类型   | 说明                                   |
| ---------- | -------------------------------------- |
| 世界观设定 | 地理、势力、规则、时代背景、超自然设定 |
| 角色档案   | 性格、动机、关系、经历、口癖、禁忌行为 |
| 剧情事实   | 已发生事件、已揭露信息、未揭露信息     |
| 伏笔记录   | 在哪一章埋下、指向什么、计划何时回收   |
| 写作风格   | 叙事视角、文风、节奏、对话习惯         |
| 用户偏好   | 作者喜欢的结构、禁用表达、目标读者类型 |

重点是：**记忆需要结构化，不是单纯把全文塞进上下文。**

------

### 2. 章节编辑能力

现有章节编辑工具可以作为系统入口，但后续需要补充几个能力：

| 功能         | 说明                                         |
| ------------ | -------------------------------------------- |
| 章节正文编辑 | 当前章节的写作、改写、润色                   |
| 章节摘要生成 | 每章结束后自动提炼关键事实                   |
| 章节状态记录 | 草稿、已确认、待修改、废弃版本               |
| 局部重写     | 只改一段，不影响其他内容                     |
| 上下文引用   | 写第 30 章时可以调用第 3、8、17 章的相关信息 |

章节工具不应该只是文本编辑器，而应该逐步变成：**章节 + 记忆 + 剧情状态的管理界面。**

------

### 3. 伏笔管理能力

这是长篇小说 Agent 的关键卖点之一。

伏笔不能只靠模型“记得”，需要单独建模。

| 字段         | 示例                           |
| ------------ | ------------------------------ |
| 伏笔名称     | 女主小时候的玉佩               |
| 首次出现章节 | 第 2 章                        |
| 表面含义     | 家族遗物                       |
| 真实含义     | 王族血脉证明                   |
| 当前状态     | 已埋下，未解释                 |
| 回收计划     | 第 41 章揭露                   |
| 关联角色     | 女主、反派、皇室               |
| 风险提示     | 第 16 章中反派不能提前知道真相 |

这样系统才能在写作时提醒：

> 当前章节涉及皇室线，但“玉佩真实含义”尚未揭露，避免提前暴露。

------

### 4. 人设一致性能力

角色一致性需要从两个层面实现。

#### 角色设定层

每个角色有固定档案：

| 类型     | 内容                       |
| -------- | -------------------------- |
| 基础信息 | 年龄、身份、背景           |
| 性格特征 | 冷静、谨慎、嘴硬心软       |
| 行为边界 | 不会主动背叛朋友           |
| 说话方式 | 短句、少解释、讽刺感       |
| 成长阶段 | 前期逃避责任，中期开始承担 |

#### 章节检查层

每写完一章，系统检查：

| 检查项                 | 示例                           |
| ---------------------- | ------------------------------ |
| 角色行为是否突兀       | 一直谨慎的人突然无理由冲动     |
| 角色知道的信息是否越界 | 某角色知道了他不该知道的秘密   |
| 角色关系是否跳跃       | 两人关系没有铺垫就突然亲密     |
| 成长变化是否有过程     | 黑化、和解、觉醒是否有事件支撑 |

这里更适合做成“检查器”，而不是一开始就让 Agent 自动修所有问题。

------

### 5. 剧情连续性检查

长篇小说最容易出现的问题是前后矛盾。

需要检查：

| 类型       | 示例                                     |
| ---------- | ---------------------------------------- |
| 时间线矛盾 | 第 5 章说三天后，第 6 章却写成第二天     |
| 地点矛盾   | 角色前一章在京城，下一章无解释出现在边境 |
| 物品矛盾   | 武器已经损坏，后面又直接使用             |
| 信息矛盾   | A 不知道秘密，但突然参与讨论             |
| 关系矛盾   | 已经决裂的两人没有铺垫又合作             |

这一块可以先做“提示问题”，后续再做“自动修复建议”。

------

## 二、系统可以拆成几个 Agent

不建议一开始做成一个万能 Agent，而是拆成多个职责清晰的模块。

### 1. 规划 Agent

负责小说整体规划。

主要功能：

| 功能         | 说明                         |
| ------------ | ---------------------------- |
| 生成大纲     | 卷、大篇章、章节结构         |
| 拆解剧情线   | 主线、感情线、成长线、反派线 |
| 安排节奏     | 哪几章铺垫，哪几章爆点       |
| 制定章节目标 | 当前章要完成什么剧情任务     |

输出结果不直接等于正文，而是写作计划。

------

### 2. 写作 Agent

负责根据章节目标生成正文。

输入包括：

| 输入         | 说明                 |
| ------------ | -------------------- |
| 当前章节目标 | 本章要发生什么       |
| 相关记忆     | 涉及角色、伏笔、设定 |
| 上章摘要     | 保证衔接             |
| 写作风格     | 文风、视角、节奏     |
| 禁止事项     | 不能提前揭露某秘密   |

输出正文草稿。

------

### 3. 记忆 Agent

负责维护小说数据库。

主要功能：

| 功能         | 说明                       |
| ------------ | -------------------------- |
| 提取章节事实 | 谁做了什么，发生了什么变化 |
| 更新角色状态 | 关系、心理、目标变化       |
| 更新伏笔状态 | 新增、推进、回收           |
| 更新世界设定 | 新出现的规则、地点、组织   |
| 生成章节摘要 | 供后续章节检索             |

它不负责写正文，而是负责让系统“记住”。

------

### 4. 检查 Agent

负责发现问题。

主要检查：

| 检查方向   | 说明                         |
| ---------- | ---------------------------- |
| 人设一致性 | 角色行为是否符合设定         |
| 剧情连续性 | 时间、地点、事件是否矛盾     |
| 伏笔状态   | 是否忘记、提前暴露、重复解释 |
| 信息权限   | 角色是否知道了不该知道的事   |
| 风格一致性 | 文风是否突然变化             |

第一阶段只需要输出问题列表，不需要自动修改。

------

### 5. 修改 Agent

负责根据检查结果修改正文。

功能包括：

| 功能         | 说明                 |
| ------------ | -------------------- |
| 局部改写     | 只修改问题段落       |
| 风格统一     | 保持文风一致         |
| 补充铺垫     | 添加必要过渡         |
| 删除冲突内容 | 去掉与设定冲突的描写 |
| 对比版本     | 展示修改前后差异     |

这个模块可以放到后期，不适合一开始就做复杂。

------

## 三、推荐阶段拆分

### 阶段 1：章节编辑 + 基础记忆

目标：让系统能围绕章节进行编辑，并保存基本信息。

优先实现：

| 功能         | 说明                     |
| ------------ | ------------------------ |
| 创建小说项目 | 保存小说名称、简介、类型 |
| 创建章节     | 支持章节标题、正文、状态 |
| 章节摘要     | 每章保存简短摘要         |
| 角色卡片     | 支持手动创建角色设定     |
| 世界观设定   | 支持手动维护基础设定     |

暂不实现：

| 暂不做         | 原因               |
| -------------- | ------------------ |
| 自动长篇规划   | 太容易牵扯多个模块 |
| 自动伏笔回收   | 依赖记忆系统成熟   |
| 多 Agent 协作  | 调试复杂度高       |
| 自动一致性修复 | 错误来源难定位     |

这一阶段重点是：**先把数据结构和编辑流程跑通。**

------

### 阶段 2：章节摘要与结构化记忆

目标：每写完一章，系统能自动提取关键信息。

新增功能：

| 功能             | 说明                           |
| ---------------- | ------------------------------ |
| 自动提取角色变化 | 如关系变化、目标变化、情绪变化 |
| 自动提取剧情事实 | 当前章发生的重要事件           |
| 自动提取新设定   | 新地点、新组织、新规则         |
| 自动提取伏笔候选 | 识别可能需要后续回收的信息     |
| 章节记忆确认     | 用户确认后再写入长期记忆       |

关键设计点：

> AI 提取的信息不能直接进入正式记忆，应该先进入“待确认区”。

否则后续会出现错误记忆污染。

------

### 阶段 3：上下文检索能力

目标：写新章节时，系统能自动找到相关旧内容。

需要实现：

| 功能         | 说明                                |
| ------------ | ----------------------------------- |
| 章节检索     | 根据当前章节目标找相关历史章节      |
| 角色检索     | 找出当前出场角色的设定和历史行为    |
| 伏笔检索     | 找出与当前情节相关的未回收伏笔      |
| 设定检索     | 找出相关世界观规则                  |
| 上下文包生成 | 把检索结果整理成写作 Agent 可用输入 |

这里的重点不是模型能力，而是**上下文包设计**。

例如：

```text
当前章节上下文包：
1. 上一章摘要
2. 当前章节目标
3. 出场角色设定
4. 最近相关事件
5. 未回收伏笔
6. 禁止提前揭露的信息
7. 写作风格要求
```

------

### 阶段 4：一致性检查

目标：写完章节后，系统能检查问题。

新增功能：

| 功能         | 说明                   |
| ------------ | ---------------------- |
| 人设检查     | 角色行为是否突兀       |
| 时间线检查   | 时间是否连续           |
| 信息权限检查 | 角色知道的信息是否合理 |
| 伏笔检查     | 是否遗漏或提前暴露     |
| 设定检查     | 是否违反世界观规则     |

输出格式可以固定为：

```text
问题类型：
涉及位置：
问题说明：
关联设定：
严重程度：
修改建议：
```

这一阶段仍然不建议自动修改正文，先把“发现问题”做好。

------

### 阶段 5：辅助修改与版本管理

目标：系统不仅能发现问题，还能辅助修复。

新增功能：

| 功能         | 说明             |
| ------------ | ---------------- |
| 生成修改方案 | 给出多个修复方向 |
| 局部重写     | 只修改指定片段   |
| 修改对比     | 展示改动位置     |
| 版本回滚     | 保留旧版本       |
| 修改理由记录 | 说明为什么这样改 |

这里需要版本管理，否则 AI 修改正文后很难追踪变化。

------

### 阶段 6：长篇规划能力

目标：让系统支持更长周期的创作管理。

新增功能：

| 功能         | 说明                       |
| ------------ | -------------------------- |
| 分卷规划     | 每卷目标、冲突、结尾       |
| 主线推进表   | 每章推进了哪些主线         |
| 角色成长线   | 角色每个阶段的变化         |
| 伏笔生命周期 | 埋设、推进、误导、回收     |
| 节奏分析     | 爽点、铺垫、高潮、过渡分布 |

这个阶段再接近“长篇小说 Cursor”的完整形态。

------

## 四、早期不建议做的功能

| 功能              | 不建议原因                   |
| ----------------- | ---------------------------- |
| 一键生成整本小说  | 不可控，质量难保证           |
| 自动决定所有剧情  | 用户参与感弱，容易跑偏       |
| 多 Agent 同时协作 | 调试困难，问题来源不清       |
| 复杂知识图谱      | 前期维护成本高               |
| 自动重写全章      | 容易破坏用户原文             |
| 完整 RAG 系统     | 前期数据结构没稳定前容易返工 |
| 复杂 UI 面板      | 功能没稳定前 UI 变化频繁     |

前期核心不是“功能炫”，而是让作者能稳定完成：

**写章节 → 提取记忆 → 检索上下文 → 检查问题。**

## 六、早期产品形态

### MVP 页面可以很简单

| 页面       | 功能                 |
| ---------- | -------------------- |
| 项目页     | 创建小说项目         |
| 章节编辑页 | 写章节、生成摘要     |
| 角色页     | 管理角色卡           |
| 设定页     | 管理世界观           |
| 记忆页     | 查看章节提取出的事实 |
| 检查页     | 查看当前章节问题     |

### 第一版核心流程

```text
创建项目
↓
创建角色和基础设定
↓
写第一章
↓
生成章节摘要
↓
提取角色变化 / 剧情事实 / 伏笔候选
↓
用户确认写入记忆
↓
写下一章时自动带入相关上下文
```

这个流程可以验证系统最重要的能力：**章节和长期记忆是否能闭环。**

------

## 七、讨论阶段的关键分歧点

| 问题                         | 两种方向                               |
| ---------------------------- | -------------------------------------- |
| 记忆是自动写入还是用户确认？ | 自动效率高，但容易污染；确认更稳       |
| Agent 是一个还是多个？       | 一个开发快；多个职责清晰               |
| 先做写作还是先做检查？       | 写作有展示效果；检查更能体现长期一致性 |
| 数据结构先简单还是直接复杂？ | 简单方便迭代；复杂适合长篇管理         |
| 是否支持全文向量检索？       | 有利于长篇，但前期成本较高             |

现阶段更适合围绕这些问题继续拆分，而不是一次性确定完整架构。
